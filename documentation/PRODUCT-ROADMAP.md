# FrontDesk — Product Roadmap

**Product:** FrontDesk
**Document:** Product Roadmap
**Current Version:** v0.1
**Status:** Draft
**Last Updated:** 2026-08-26

---

# 1. Purpose

This document defines the planned evolution of FrontDesk from the initial validation product into the long-term AI Business OS vision.

The roadmap exists to:

- protect v0.1 scope,
- prioritize features,
- define product evolution,
- prevent feature creep,
- communicate future direction,
- and establish dependencies between capabilities.

The roadmap is directional.

Future versions must be validated against:

- customer feedback,
- product analytics,
- technical feasibility,
- infrastructure cost,
- market conditions,
- and business performance.

Version numbers do not represent guaranteed release dates.

---

# 2. Product Vision

FrontDesk's long-term vision is:

> **Become the digital operating system for small and local businesses.**

3. Roadmap Philosophy

FrontDesk should not build the entire vision immediately.

The development strategy is:

Earn the right to expand.

Each stage should prove the value of the previous stage before introducing significantly more complexity.

9. v0.1 Success Criteria

The primary question is:

Can a non-technical business owner successfully bring an existing business into FrontDesk and receive customer interaction?

Key validation signals:

Businesses successfully import or enter information.
Businesses publish.
Businesses generate/use QR.
Customers visit.
Customers initiate enquiries.
Owners return to update information.
Owners understand the value without requiring technical assistance.

52. Feature Promotion Rule

A feature moves from future roadmap into active development only when at least one of these conditions is satisfied:

Strong customer demand.
Validated business problem.
Important retention driver.
Important revenue opportunity.
Required infrastructure for another validated feature.
Critical security/reliability requirement.
53. Feature Deferral Rule

A feature should remain deferred when:

it is interesting but unvalidated,
it increases complexity significantly,
it does not improve the core user journey,
it requires expensive infrastructure,
or another feature must be validated first.
54. Feature Kill Rule

A feature can be removed from the roadmap if:

users don't need it,
usage is consistently low,
it is too expensive to maintain,
it creates disproportionate complexity,
or a better solution replaces it.

56. Cost-Conscious Development Strategy

FrontDesk is initially intended to be developed with minimal or zero paid infrastructure.

Therefore roadmap stages should consider:

free/open-source models,
local development,
self-hostable services,
free database tiers,
free hosting where appropriate,
open-source libraries,
provider abstraction.

However:

"Free" must not override security, reliability, or legal requirements for production use.

57. AI Cost Strategy

AI should be abstracted behind an internal service.

Conceptually:

Application
    ↓
FrontDesk AI Layer
    ↓
Provider Adapter
    ├── Local Model
    ├── Free Tier API
    └── Paid API

This prevents the product from becoming dependent on a single AI provider.

58. Infrastructure Evolution
v0.1

Simple architecture.

Goal:

Validate product.

v0.2–v0.3

Improve reliability and data architecture.

v0.4–v0.6

Introduce background jobs, integrations, automation, and analytics infrastructure.

v0.7+

Introduce agent infrastructure, permissions, event systems, APIs, and ecosystem capabilities.

59. Roadmap Risk

The biggest roadmap risk is:

Trying to build the v1.0 vision during v0.1.

The current FrontDesk vision contains enough functionality to become a very large platform.

Therefore:

Vision ≠ Current Scope

The vision guides architecture.

The MVP validates the business.

61. Roadmap Decision Gate

Before moving from one major stage to the next, evaluate:

Product
Are users adopting it?
Are users returning?
Are users receiving value?
Business
Will users pay?
Is acquisition possible?
Is retention improving?
Technical
Is the architecture stable?
Are infrastructure costs manageable?
Are data models reusable?
Customer
What do users repeatedly ask for?
What problems remain unsolved?
62. Major Product Gates
Gate 1
Import → Publish → Customer Interaction

If this fails:

Do not build advanced operations.

Gate 2
Business → Returns → Updates

If this fails:

Do not assume CRM/automation will solve retention.

Gate 3
Operations → Repeated Usage

If this succeeds:

Introduce automation.

Gate 4
Automation → Trust

If users trust automation:

Introduce proactive AI.

Gate 5
AI → Controlled Actions

If AI actions are reliable:

Introduce agents and ecosystem capabilities.
